## 3. Ответы на контрольные вопросы (Приложение В)

Каждый ответ — 250–450 слов, со ссылками на собственные результаты (TxID, логи, тесты) там, где это уместно. Обязательные тезисы:

**1. Жизненный цикл Execute → Order → Validate → Commit, где транзакция может стать недействительной, роль MVCC.**
Execute: proposal, симуляция, RW-set, endorsements; отказ здесь (ошибка chaincode, не собрана политика) означает, что транзакция вообще не попадает в ledger. Order: orderer не исполняет бизнес-логику, проверяет право отправителя писать в канал и формат, формирует блоки. Validate: VSCC — `ENDORSEMENT_POLICY_FAILURE`; MVCC — `MVCC_READ_CONFLICT`, если версия ключа из Read Set (block_num, tx_num) устарела; `PHANTOM_READ_CONFLICT` для range-запросов; дубликат TxID, неверные подписи. Commit: в Blockchain попадает весь блок, включая невалидные транзакции с кодами; к World State применяются только write-set валидных. MVCC — оптимистичная конкурентность, защита от lost update и двойного исполнения. Если делалось MVCC-демо — сослаться на его TxID.

**2. Endorsement Policy vs авторизация в chaincode; может ли транзакция удовлетворять EP и нарушать бизнес-логику.**
EP определяет, какие организации должны подтвердить результат исполнения, и проверяется при валидации; она ничего не говорит о том, кто вызвал функцию и разрешено ли ему это. Авторизация вызывающего (MSP, атрибуты, идентичность, состояние объекта) — ответственность chaincode. Ответ «да» на собственном примере `paymentvuln`: Org2 выполнила Submit, оба peers подписали, EP AND выполнена, инвариант нарушен (OWASP SC01/SC03). Упомянуть state-based endorsement как дополнительный механизм.

**3. Channel vs Private Data Collection.**
Channel: отдельный ledger, отдельное членство и конфигурация, участники вне канала не знают даже о факте транзакций; orderer видит все транзакции канала; высокие административные издержки. PDC: внутри канала, данные хранятся только у членов коллекции в side DB, в блоках — хэши для всех участников и orderer, передача через gossip и transient, `blockToLive`, `memberOnlyRead/Write`, collection-level EP, purge. Когда что: канал — если нужно скрыть сам факт отношений и транзакций; PDC — если участники общие, а конфиденциальна часть данных (наш случай — реквизиты видит только банк-отправитель, банк-получатель может сверить хэш). Нюансы: утечка через transient к endorsers не-членов; перебор хэша низкоэнтропийных данных без соли.

**4. version, sequence, package ID; зачем увеличивать sequence; сохранность World State.**
version — метка, сама по себе ничего не запускает; sequence — счётчик изменений определения chaincode, растёт ровно на 1 при любом изменении (код, политика, коллекции, init-required), все организации утверждают одно и то же значение — это защищает от рассинхронизации и повторного применения старых определений; package ID = label + хэш пакета, связывает утверждение организации с конкретным установленным кодом на её peers. World State принадлежит namespace chaincode, а не пакету, поэтому сохраняется; совместимость обеспечивает разработчик (правила из `payment-v2-compat.md`, ленивая миграция). Сослаться на свою демонстрацию отказа при `--sequence 3`.

**5. Raft CFT vs SmartBFT BFT; почему остановка одного orderer не доказывает устойчивость к Byzantine behavior.**
Raft: n = 2f + 1, лидерский протокол, узлы предполагаются честными, выдерживает остановки меньшинства; злонамеренный лидер может цензурировать или переставлять транзакции. SmartBFT: n = 3f + 1, подписанные сообщения, кворум ⌈(n+f+1)/2⌉, проверка предложений лидера, view change, блоки подписываются кворумом. Остановленный узел просто молчит — это crash fault; византийский узел может рассылать противоречивые сообщения, подписывать конфликтующие блоки, задерживать или выборочно доставлять данные. Проверка BFT требует внедрения таких ошибок или формальных методов. Сослаться на свои результаты: отказ 1 узла — работа продолжается, 2 узла — нет кворума.
